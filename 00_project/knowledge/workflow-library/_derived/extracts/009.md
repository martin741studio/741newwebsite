# 009 Anthropic Just Revealed 10 NEW Rules for Claude Skills
Source: Jay E | RoboNuggets, 2026-10-05, https://www.youtube.com/watch?v=VQyYzLJ6xos
Reliability: Medium. Practitioner summarizing Anthropic's updated skills guide. He sells a community and a free PDF with a "skill creator plus" skill. Claude 5.5 behavior claims are attributed to Anthropic's guide.

## Rules (IF situation THEN action. Why.)
- R1 IF a skill file is long THEN keep SKILL.md under 500 lines and split the rest into linked files. SKILL.md works like a contents page. Claude opens other files only at the step that needs them.
- R2 IF a file points to a second file that points to a third THEN expect Claude to preview only the first 100 lines of the third. Keep references one level deep.
- R3 IF a file is over 100 lines THEN put a short contents list at the very top. Claude can then jump to the right section even if it previews only the first 100 lines.
- R4 IF a step is risky THEN give more detail and guardrails (low freedom, an exact script, for example raising an invoice or tax documents). IF it is not consequential THEN leave room (high freedom, plain instructions). Medium freedom is a template with a few settings, for example a weekly report. One skill can mix all three.
- R5 IF you use skills on several models THEN test on each model you use. Haiku question: is there enough guidance? Sonnet: is it clear and efficient? Opus and Fable: does it avoid over-explaining? Test only the skills you rely on most or where a mistake is costly, because testing is expensive.
- R6 IF a skill was written for an older model THEN test it with fewer guidelines. It may be too prescriptive for the newest models and make output worse.
- R7 IF a skill opens with a definition Claude already knows (for example what an invoice is) THEN delete it. Keep only what Claude cannot work out: your prices, terms and internal rules.
- R8 IF you write a skill description THEN write it in the third person ("creates client invoices and sends payment reminders"), not "I can help you with...". Claude reads the description to choose a skill.
- R9 IF a job has many steps THEN write a checklist that Claude copies into its reply and ticks off. Add go-back lines, for example: if any total does not match the job list, go back to step 2.
- R10 IF output quality matters THEN add a feedback loop: run the skill, check against a short checklist, fix what fails, repeat until it passes. It works for non-code work such as a style guide (consistent terms, standard example format, all required sections).
- R11 IF output must be well defined THEN use one of three patterns: a template (strict or with a default), input and output example pairs, or a conditional workflow (a fork based on task conditions).
- R12 IF a skill will be shared THEN do not assume tools are installed. List the exact packages and add install instructions.
- R13 IF a rule must hold every time (for example never send an invoice above $10,000 without a person's sign-off) THEN move it from the skill into a hook. A hook runs code at a set moment, whether or not Claude follows the skill. A hook can live inside the skill.

## Mistakes to avoid
- Do not bury key guidelines deep in a long file. Claude may never read them.
- Do not nest references more than one level.
- Do not write "never do X" in capitals when the cost of failure is high. Use a hook.
- Do not over-prescribe for the newest models.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- Third-person descriptions, checklists with go-back lines, and style-guide feedback loops apply to client deliverables.
- Degrees of freedom: lock down invoices and legal text, leave brainstorming open.
- Hooks need Claude Code. The video does not say if Cowork supports them.
