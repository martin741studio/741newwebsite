# 010 These Mods Take Claude Code to Another Level
Source: Mark Kashef, 2026-10-05, https://www.youtube.com/watch?v=UcvD53jqHRU
Reliability: Medium-low for general use. Practitioner demo of two advanced, hacky mods (reverse engineering Codex tools). Sells an early adopters community. The speaker says it took about an hour of iteration, so the result is not a simple recipe.

## Rules (IF situation THEN action. Why.)
- R1 IF you want a feature from another tool (for example Codex) THEN ask Claude to watch that tool while it runs and listen for the services it calls. Tools can often be exposed as an MCP, so another LLM can use them through a bridge.
- R2 IF Claude says a connection is impossible THEN do not accept it. Ask it to inspect the installed mod authoring API and the CLI help first, and to separate "tool missing in this chat" from "capability that can be built". Claude often finds it is possible when it checks.
- R3 IF a permission prompt from another tool keeps interrupting THEN build a persistent local helper (a bridge) that keeps a live connection to the other session and handles approvals in the background.
- R4 IF a mod is experimental THEN make it ask before using an app for the first time with three choices: allow for this chat, always allow, don't allow.
- R5 IF you want to switch a mod off and on THEN add a toggle (his example: /codex-cu on). Keep it on by default for each chat if that is your goal.
- R6 IF you build a complex mod THEN start the prompt with the north star goal. Say the exact outcome, then add the technical detail, a test plan (for example a calculator task), troubleshooting steps, and where files should go so the mod library does not get bloated.
- R7 IF you start a mod prompt THEN tell Claude to load the plugin-authoring skill first and re-read how mods work, so it is primed.
- R8 IF Claude refuses or stalls on a hard mod THEN use /goal with explicit tests, for example create one thread, send a plan, watch it finish, then two threads. It burns many tokens but pushes Claude to test its own work.
- R9 IF you want a lead session to run helper sessions on different models THEN build a threads mod: each helper is a normal Claude Code session with its own model, name, and a sidebar entry. Tell it to skip permission prompts.
- R10 IF you use helper sessions THEN track stuck sessions and log the API-equivalent cost. Make threads remote-control eligible if you want to manage them away from the computer.
- R11 IF you plan work across models THEN the speaker's example: plan with Opus, pass notes to a Sonnet helper, final check by Haiku.
- R12 IF you want to learn Claude Code details THEN run `claude --help` so Claude can read its own options.

## Features and facts mentioned (with version or date if given)
- Codex's computer use can click and type in apps in the background without taking over your mouse. The mod lets Claude orchestrate those tools. It uses the existing Codex app subscription, so no extra agents API cost.
- Claude desktop app cannot spin up multiple model threads on its own (per the speaker). The threads mod adds a side pane with the lead model, sub-threads, spend and a place to steer all threads.
- Models named in his example prompts: Opus 5.5, GPT-6 Astra, Sonnet 5.5.
- Resources (code, prompts) are offered in a GitHub repo linked in the description.

## Mistakes to avoid
- Do not expect a one-shot build. He needed several tries.
- Do not leave tools set for permission prompts per action. It breaks the flow.
- Do not accept "not possible" without checking.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- none for daily use. These mods are technical and unofficial. The one general idea: ask Claude to inspect before it says "impossible".
