# 031 Claude Code New Features, Explained
Source: Greg Isenberg, 2026-08-17, https://www.youtube.com/watch?v=SkY-tR9kf-k
Reliability: Medium. Practitioner; sponsored by Anthropic (he says so). Teaches an "AI employee" setup with a med-spa example. Offers prompts in show notes. Some model names (Opus 4.8, Fable 5) come from captions.

## Rules (IF situation THEN action. Why.)
- R1. IF you want Claude to act like an employee THEN give it nine things: workspace (repo), memory (context), brief (plan mode), ticket, eyes (preview and inspection), review, schedule (routines), permissions, and skills/connectors/hooks.
- R2. IF you start a project THEN use the Code tab in the desktop app (less overwhelming than the terminal) and select the project folder.
- R3. IF you build a project workspace THEN create folders `/app`, `/context`, `/customers`, `/demos`, `/routines` and three root files: `CLAUDE.md` (how Claude works), `roadmap.md` (what matters now), `review.md` (how to judge work before it ships).
- R4. IF you set up the workspace THEN prompt: "Help me set up this repo as an AI employee workspace" and give product, buyer, pain, promise, and current goal. Add "ask me for any missing context that would materially change the setup and keep the first version simple".
- R5. IF you write CLAUDE.md THEN add a working style (small reviewable changes, explain the plan before editing when behavior changes, keep to existing code style, run checks, summarize what changed, what was tested, what needs human review), business context, and a quality bar.
- R6. IF you write roadmap.md THEN state this week's goal and an explicit out-of-scope list (his example: payments, CRM integration, admin dashboards, multi-user permissions).
- R7. IF you write review.md THEN use a checklist: matches the roadmap, small enough to review, main flow works, mobile layout, form errors, auth/payment/production-data risk, no extra complexity; for landing pages: offer clear in 5 seconds, CTA visible, copy specific to the buyer, customer language.
- R8. IF the task affects product behavior THEN use plan mode first. Ask Claude to read CLAUDE.md, roadmap.md, review.md, then list files to change, the smallest clean implementation, user experience, risks, how to verify, and what is left out. End with "wait for my approval before editing".
- R9. IF you assign work THEN write a ticket: one task, one finish line, one reviewable change, with scope and boundary. Avoid vague tickets ("make the app better", "add AI", "build the whole thing").
- R10. IF Claude finishes THEN ask it to implement as one focused change, run relevant checks, open the desktop preview, and report what changed, what it tested, and what needs human review. Check the diff view for surprising changes.
- R11. IF you want QA THEN prompt Claude to start the app and inspect the flow from the buyer's view (what is understood in 5 seconds, what feels confusing or low trust, does the form work). Then "make one focus pass to improve the highest impact issue".
- R12. IF you review THEN ask Claude to use review.md as the standard and sort findings into must fix, should fix, okay to ship. Use `/review`; use `/ultrareview` for risky features such as authentication or payments.
- R13. IF you want recurring work THEN start with a low-risk routine: a weekday 7 a.m. morning brief written to a context file (top customer pain, one product risk, one build task, one question for customers; no code edits, under 500 words). Add a Friday 3 p.m. weekly ops review. Add a loop that reviews each opened pull request against review.md.
- R14. IF you run parallel work THEN give each session one clear assignment with worktree isolation and a defined handoff (root cause, files changed, checks run, what to review).
- R15. IF you set permissions THEN split into safe actions (read, plan, local tests, small branch, docs, draft PR), ask-first actions (dependencies, migrations, auth, payments, deleting files), and human-owned actions (production deploys, customer data, billing, security). Start conservative.

## Features and facts mentioned (with version or date if given)
- Routines (scheduled recurring prompts), desktop preview, diff view with comments, `/review`, `/ultrareview` (remote session).
- Hooks: run formatting after edits, tests before PR summary.
- Skills examples: landing page teardown, customer notes (extract customer words, objections, buying triggers), demo script.
- Plan mode suggested with Fable over Opus for planning.
- Seven-day plan: day 1 repo brain; 2 plan mode; 3 one visible improvement; 4 preview loop; 5 review; 6 send to 10 people and file replies in `/customers`; 7 first routine.

## Mistakes to avoid
- Vague tickets. Giant batches of changes. Yolo mode. Starting with production-code routines instead of read-only briefs.
- Skipping the "out of scope" list.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- The folder pattern (context, customers, demos, routines + CLAUDE.md, roadmap.md, review.md) fits a client project folder.
- review.md as a QC checklist for client deliverables; must/should/okay sorting.
- Morning brief and weekly ops routines map to agency reporting.
- Customer-notes skill: pull exact customer wording for copy.
- Permission tiers: safe, ask first, human-owned.
