# 023 How the Claude Code team uses Claude Code
Source: Claude (official channel), 2026-09-02, https://www.youtube.com/watch?v=S-sYlFiGFv8
Reliability: High (official Anthropic channel, team members talking). Conversational; few concrete commands. Thin on rules.

## Rules (IF situation THEN action. Why.)
- R1. IF you work with current models THEN give a goal, not step-by-step control. The team moved from watching each tool call to a zoomed-out view: "I have a goal", give it to the model.
- R2. IF a feature compensates for a model weakness THEN expect to delete it later. Example: the to-do list helped around Sonnet 3.5 for long tasks; a year later it was not needed. Stay unattached to what you build.
- R3. IF work must continue when your laptop is off THEN run Claude in the cloud (Claude Code on the web, hosted containers) and use routines. The team moved from local to remote dev boxes to cloud.
- R4. IF you want recurring work THEN use a routine. Example given: every day, read all feedback, bucket it by importance, and fix the ones Claude is highly confident about.
- R5. IF the task is a large search (bugs, performance issues, research, trip planning) THEN fan out many subagents, then filter the results back down. The speaker calls it a MapReduce problem. This uses test-time compute.
- R6. IF fan-out gives many findings THEN add an adversarial review per finding: ask Claude to judge it from three perspectives and keep only real ones.
- R7. IF you build a workflow THEN let Claude write the orchestration code. Code (for loops) gives deterministic coverage, so no item is skipped, while subagents give agentic reasoning. This raised the speaker's trust.
- R8. IF Claude creates a change THEN require verification. The Claude Code team has Claude test the PR and send screenshots. Another example: ask Claude to record itself using the TUI.
- R9. IF humans review code THEN focus them on the big picture (why an API is shaped a certain way, service boundaries). Claude handles the nit-picks autonomously.
- R10. IF you build a product with Claude THEN make the dev environment and dev loop easy for Claude to use, so it can build and test end to end by itself.
- R11. IF you need feedback on a tool THEN add events to it and let Claude monitor usage and feedback (metrics, Slack, GitHub issues) and ping you.
- R12. IF you ask Claude to improve something (such as a funnel) THEN ask for ideas at the higher level and give your idea only as an example.

## Features and facts mentioned (with version or date if given)
- Claude Tag: a Slack-native Claude agent. One speaker does 70 to 80% of work there; 20% in the TUI or desktop app.
- Claude Tag shows messages sent by a tool; the full transcript is behind a link.
- Primitives named: auto mode, memory, workflows, routines, loops, AskUserQuestion tool, artifacts, code review bot.
- Workflows came from the code review fan-out.
- The AskUserQuestion tool was hard to design; now the speaker often uses an HTML artifact that asks questions with diagrams and mockups.
- Product shelf life: the technology shifts "every two months".

## Mistakes to avoid
- Over-supervising transcripts and individual tool calls.
- Building heavy scaffolding that the next model makes obsolete.
- Having humans spend review time on nit-picks.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- Routines for daily or weekly jobs (feedback sorting, reports) that run without your laptop.
- Fan-out then verify pattern for research: many searches, agents rank, agents verify, one summary. Good for competitor or keyword research.
- Slack-native agent idea: Claude has team context (decisions, product background) and works from your phone.
- Ask Claude for an HTML artifact that asks questions and shows mockups.
