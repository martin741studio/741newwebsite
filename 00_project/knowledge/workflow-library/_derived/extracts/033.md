# 033 Every Claude Code Skill I Use to Drive My Entire Development Process
Source: Cole Medin, 2026-08-13, https://www.youtube.com/watch?v=MbiMwgbGdxw
Reliability: Medium. Practitioner showing his own skill library (PIV loop). Sponsor read (Agora) and promotes a paid community. High-level; he runs no skill in the video. Developer focus.

## Rules (IF situation THEN action. Why.)
- R1. IF you want a coding process THEN use two loops. The outer loop plans a larger scope once per epic (PRD, spec, tickets). The inner loop handles one ticket at a time (prime, plan, implement, validate, pull request).
- R2. IF you start a new scope of work THEN write a PRD first with a PRD skill. The skill interviews you and covers the what and the why only: target user, problem, hypothesis, evidence. It does not cover the how.
- R3. IF the PRD is done THEN write the spec (architecture, the how) in a separate conversation with its own skill and template. Two separate conversations, two documents.
- R4. IF you have a PRD and a spec THEN use a "slice epic" skill that takes both as input, maps dependencies and parallel work, and creates bite-sized tickets (markdown files, GitHub issues, or Jira tickets). Do not overwhelm the agent with a too-big ask per conversation.
- R5. IF you start a ticket THEN run a "prime codebase" skill first to load context. The agent is "pretty stupid at the start of a conversation". Priming can focus on the ticket or on one area (such as the front end).
- R6. IF you plan the ticket THEN run the plan skill in the same conversation as the prime. The agent should interview you and research the codebase before it writes the plan. Reason: LLMs confidently make terrible assumptions.
- R7. IF you write plans THEN use a fixed template: feature description, user story, problem statement, solution statement, out of scope and non-goals, context references, files to touch, task-by-task plan, testing strategy. Fixed templates make skills reliable and repeatable.
- R8. IF you write the plan THEN define the validation strategy before any code: unit tests, integration tests, edge cases, exact commands for lint, type check, tests, and manual validation (for example browser automation). He calls this "test-driven development for agents". The agent iterates on its own work, so you intervene less and get less AI slop.
- R9. IF you review a plan THEN focus mostly on the validation strategy and on whether the agent understands what you want. Be specific about the end (what done looks like), not the means.
- R10. IF the plan is approved THEN implement it in a brand-new conversation with the plan path as the only argument. Planning conversations are long; a new one avoids context rot (the "dumb zone").
- R11. IF the agent says it is done THEN still review the code and test manually. A validation plan does not guarantee a perfect job. End each ticket with a pull request, review it, merge, and go to the next ticket.
- R12. IF a skill needs changes THEN ask the coding agent to edit it from a plain description. He never hand-edits skills.
- R13. IF you already have a process THEN pick single skills or ideas from a library. Do not adopt a whole framework (GitHub Spec Kit, Gas Town) because they force one process on you.
- R14. IF your skills take input THEN give them an argument hint so the slash command shows what to pass in (for example product idea, spec path, PRD path).

## Mistakes to avoid
- Mixing the what/why with the how in one document.
- Planning and implementing in one long conversation.
- Letting the agent assume instead of interviewing you.
- Trusting the validation plan with no human review.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- Outer/inner loop maps to agency work: brief and strategy once per client, then one deliverable at a time.
- Interview-first skills (PRD, plan) reduce wrong assumptions in client deliverables.
- Fixed templates per document type for repeatable output.
- Define "done" and the check up front for each deliverable.
- New conversation per stage to keep context clean.
