# 013 Everything You Know About Skills IS OUTDATED
Source: Simon Scrapes, 2026-10-01, https://www.youtube.com/watch?v=e7TY56-yIvM
Reliability: Medium. Practitioner summarizing Anthropic's updated best-practice guide, with his own advice. Offers a free audit prompt (and a follow-up video). Closely matches video 009.

## Rules (IF situation THEN action. Why.)
- R1 IF a reference file inside a skill is over 100 lines THEN put a contents list at the top that matches its headings. Claude may read only the first 100 lines (a head -100 style read) to decide if the file helps. Rules after line 100 may be missed. To fix: go through every skill in the .claude/skills folder, find reference files over 100 lines, add the list.
- R2 IF you decide how detailed a step must be THEN ask what happens if Claude does it differently. If little changes, give high freedom (plain instructions, for example a sales call review or a LinkedIn post). If it is a preferred shape, give medium freedom (a template with settings such as charts true or false, format markdown or HTML, for example a weekly client report). If it is fragile and consequential, give low freedom (an exact script, for example raising invoices or removing members).
- R3 IF a step needs low freedom THEN use a script, not more plain text. A script runs the same on every model. Scripts are run, not read into memory, so they use no context.
- R4 IF one skill has different kinds of steps THEN mix levels. Writing the email can be high freedom while creating the invoice is low freedom.
- R5 IF you use several models THEN test the skill on each. Haiku: enough guidance? Sonnet: clear and efficient? Opus: does it avoid over-explaining? Run your most used skill on the same task with Haiku, then Opus, then Sonnet. If Haiku misses a step, make the step clearer or turn it into a script.
- R6 IF Opus does worse with the skill than without it THEN cut instructions until it does better. Older skills with numbered lists and capital letters can be too prescriptive for newer models.
- R7 IF you share a skill THEN write the intended model in the YAML front matter.
- R8 IF SKILL.md nears 500 lines THEN split content into separate files and treat SKILL.md as the contents page. Split references by area (for example finance, sales, product, marketing files) so a revenue question never loads the marketing file. For client reporting use one file per client.
- R9 IF a reference file is reachable only through another reference file THEN link it directly from SKILL.md. Keep all references one level deep. Nested files may be only partly read. You can ask Claude to find such files.
- R10 IF the order of steps matters (for example check data before building the report) THEN give a checklist that Claude copies into its reply and ticks off. If order does not matter, skip the checklist.
- R11 IF a step can fail THEN add a go-back line, for example: if citations are incomplete, return to step 3. This stops Claude from ticking a failed step.
- R12 IF you want a skill to improve itself THEN use a feedback loop: draft, check against a guide (it can be your brand voice document), note each issue, revise, repeat until it passes. When a draft fails for a reason not in the doc, have Claude suggest a new rule at the end of the run, approve it, and add it to the doc.
- R13 IF a teammate will install your skill THEN do not assume tools are installed. Write "install the required package" with the package name next to each script. Claude skips the step if already installed.

## Mistakes to avoid
- Do not give every skill the same level of detail.
- Do not nest reference files.
- Do not test a skill on one model only.
- Do not rely on tools installed on your own laptop.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- Directly useful: weekly client report as a medium-freedom template. One reference file per client. Brand voice document as the style guide for a feedback loop. Low freedom for anything touching money.
- Skills must work in a fresh Cowork session, so list dependencies.
