# 038 Why Graph Engineering will 10x your Claude/Codex
Source: Greg Isenberg, 2026-08-03, https://www.youtube.com/watch?v=JWhICz1QR8M
Reliability: Medium. Practitioner and podcast host. Conceptual framework with no tested numbers and no Claude Code commands. It uses a new buzzword, but the practical steps are simple and sound.

## Rules (IF situation THEN action. Why.)
- R1 IF a task has multiple steps, some steps can run at the same time, and the output needs checking before it matters THEN design it as a graph (jobs joined by arrows). IF it is a short brainstorm or a short email summary THEN skip the graph.
- R2 IF you start THEN draw the graph before you automate it. Use a blank Excalidraw or TLDraw board: final outcome at top, then jobs, then arrows.
- R3 IF you design the jobs THEN list what a great human would do: clarify the question, research customers, competitors, distribution, risks, check evidence, recommend.
- R4 IF two jobs do not depend on each other THEN run them in parallel. Delete fake waiting.
- R5 IF the same model writes and grades the answer THEN add a separate checker (a skeptic) as its own job. Its task is to attack weak findings and stale evidence.
- R6 IF evidence survives the skeptic THEN a merge step turns it into one recommendation.
- R7 IF the output is costly or public (customer email, public post, deploy, refund, production data) THEN add a strict human approval gate. For a private memo a light gate is enough.
- R8 IF you run it the first time THEN do it manually with separate lanes. Run it three times before you automate. If the manual version is not better, automation only makes mediocre work faster.
- R9 IF you move to Claude Code THEN let each step write a file: plan.md, customer.md, competitors.md, distribution.md, review.md, recommendation.md. This leaves a paper trail, lets you compare versions, and lets you reuse the structure.
- R10 IF you need state, checkpoints, and human-in-the-loop THEN the advanced tools are LangGraph, AutoGen GraphFlow, n8n, or make.com. Choose the tool after the workflow is clear.
- R11 IF you add agents THEN keep the smallest graph that improves quality. More agents can mean more noise and repeated wrong ideas.
- R12 IF the graph finishes THEN stop when the answer is good enough, and keep the state (notes, evidence, drafts, sources, decision) as memory for the next run.

## Features and facts mentioned (with version or date if given)
- Two meanings of "graph": a knowledge graph (relationships between things, for example Microsoft GraphRAG) and an agent graph (how work moves). The video focuses on agent graphs.
- Example graphs: startup idea research (planner, 3 researchers, skeptic, merge, human), customer support (classify, account check, docs, draft, checker, human for refunds or legal), content (research, thesis, hook, script, checker, then titles and thumbnails), coding (plan, edit, review diff, tests, browser check, human approves PR).
- Skill levels: level 1 manual lanes, level 2 Claude Code with files per step, advanced orchestration tools.

## Mistakes to avoid
- Asking one chat for research, evidence, recommendation, and grading all at once.
- Building the biggest graph for show.
- Automating a workflow you do not yet understand.
- Hunting for the perfect prompt instead of the right workflow.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- High. A client audit or page brief maps well: planner, SERP/competitor/local researchers in parallel, a checker, a merge, then human approval before delivery.
- Step-per-file output (one .md per step) fits client folders and review.
- Support or email replies: always keep a human gate for money, promises, and angry clients.
