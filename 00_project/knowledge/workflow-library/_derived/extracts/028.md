# 028 I Have Spent 1000+ Hours With Claude Code. This Is What I Learned
Source: The Coding Sloth, 2026-08-18, https://www.youtube.com/watch?v=YAsxyoTWFDA
Reliability: Medium. Practitioner opinion with tier ratings. Developer-focused, jokes, sponsor read (Brilliant), newsletter plug. Some content was recorded a month before publishing and is partly out of date (he says so).

## Rules (IF situation THEN action. Why.)
- R1. IF you open a project THEN `/init` creates CLAUDE.md. The speaker rates it mid. An experimental version (set an environment flag) interviews you and recommends skills and hooks.
- R2. IF you already have an `agents.md` file THEN import it inside CLAUDE.md instead of making a symlink.
- R3. IF you write CLAUDE.md THEN keep it small: project description, current status, coding style, working philosophy, pull request language. Add rules for the model's bad habits (his example: stop using ALL CAPS in user-facing text). He says CLAUDE.md is not make or break; skills can do the job.
- R4. IF a workflow repeats THEN make it a skill (`SKILL.md`). Use skills for best practices, workflows, and research methods. Find skills at skills.sh and GitHub repos.
- R5. IF you install skills THEN do not install a hundred. Stick to one group of skills that match your style. Same for MCPs: only install what you need.
- R6. IF a task is big THEN use plan mode (Shift+Tab). It is easier to catch a mistake in a plan than in 3,000 lines of code. IF the task is small (typo, rename) THEN skip plan mode.
- R7. IF you want to save money THEN use the smart model to write the plan and a cheaper, faster model to implement (for example Opus plans, Sonnet implements).
- R8. IF Claude implements something THEN give it a way to verify. Ask for tests first, then the implementation (otherwise it writes tests that pass its own code). Test only the important things. Also use type checkers, linters, screenshot testing, and browser testing, because Claude cannot see what it builds.
- R9. IF Claude must touch things outside the code base (GitHub, database, Slack, analytics, browser) THEN use an MCP. IF it only needs best practices THEN use a skill, not an MCP.
- R10. IF you start a new task THEN start a new session. Each medium or big task uses at least 50,000 tokens; with research, skill, or MCP it can pass 100,000. Quality dips above roughly 100,000 to 200,000 tokens ("dumb zone").
- R11. IF Claude explores files it does not need THEN tell it to stop at once. Be "stupidly specific" in prompts and name the files and sources to use.
- R12. IF Claude auto-compacts mid-task THEN start a new session. IF you compact yourself THEN tell it exactly what to keep.
- R13. IF you want recurring automation THEN use `/loop` with a time interval (like an AI cron job). His examples: pick a GitHub issue daily and open a PR; a security and bug sweep that files GitHub issues; feature brainstorming from code, PRs, and issues.
- R14. IF Claude should work until a condition is met THEN use `/goal` (for example "every test passes and no type errors"). Better on higher plans.
- R15. IF you run parallel work THEN use worktrees (one chat per worktree). Subagents get their own context window and return a summary, but they drain usage limits fast on the $20 plan.

## Features and facts mentioned (with version or date if given)
- `/voice` (talk to prompt), `/btw` (side question; Claude cannot read files or run commands for it), `/teleport` and remote control (move sessions between phone, web, terminal), `!` prefix for shell mode (Claude sees the output), `/context`, `/compact`, `/radio` (lo-fi music).
- Ultra plan mode existed and was removed.
- Default skills: code review, security review.
- A Fable model needs usage credits. Context limits mentioned: about 300K and 1M tokens.
- Named skill authors: Matt Pocock (grill-with-docs, improve codebase architecture), a Cursor "thermonuclear code quality review" skill.
- Alternatives named: Codex, OpenCode, Pi, Cursor, VS Code Copilot, T3 Code.

## Mistakes to avoid
- Running several tasks in one long session.
- Letting Claude write tests after the code.
- Installing many skills and MCPs.
- Using plan mode for tiny tasks.
- Blindly accepting changes; ask Claude to explain each change.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- `/loop` automations (daily sweep, daily brainstorm) map to scheduled client checks.
- One task = one session keeps quality and usage low.
- Skills for repeatable client workflows; MCP only for outside systems.
- Plan first for big deliverables; skip for small edits.
