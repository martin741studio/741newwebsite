# 037 Matt Pocock's Claude Code Skills Beat Superpowers Now
Source: Eric Tech, 2026-08-07, https://www.youtube.com/watch?v=8D8ewFBJfFM
Reliability: Medium. Practitioner summary of a third-party skill library (Matt Pocock) with opinions. Promotes a paid school community. Model-strength claims are the speaker's own view. Developer-focused.

## Rules (IF situation THEN action. Why.)
- R1. IF AI output is random or misses your intent THEN collect the full context first with a "grill-me" style skill. The skill is very short and follows five rules: (1) keep asking until you and the AI share understanding; (2) work one decision-tree branch at a time; (3) ask one question at a time and wait for the answer; (4) always give a recommended answer with options; (5) do not act until you confirm.
- R2. IF you finish the interview THEN write the result down as a spec ("to spec" skill), or it is lost when the chat closes. Keep code blocks out of the spec. Reason: the agent follows code in the spec even when it is outdated; without code, it checks the real code base.
- R3. IF the spec is done THEN turn it into tickets ("to tickets" skill). Slice tickets by feature, not by layer (database, API, UI). Reason: a feature slice (for example the login page) can be tested end to end after each ticket.
- R4. IF you implement THEN use test-driven development: write tests first, see them fail, then write code. Reason: tests written after the code just match the code, including its bugs.
- R5. IF you review code THEN start a fresh context window and follow a short checklist of 12 named terms from Martin Fowler's refactoring book (examples: shotgun surgery, feature envy, data clumps). Short named terms carry deep meaning, so the skill needs no long explanation.
- R6. IF you write or edit a skill THEN prune it. Every extra word is a distraction that can cause hallucination. Go direct ("Interview me relentlessly") and use terms with deep meaning. He uses a "writing for agents" skill to do this.
- R7. IF the code base is scattered (many small functions the agent must hop through) THEN wrap related code behind one entry point so the agent reads less. Each function still keeps its own file. His example: understanding a function drops from about 10,000 tokens to about 1,000.
- R8. IF you review architecture THEN run a "deletion test": delete a function and see whether tests still pass. If yes, the function is redundant. The "improve codebase architecture" skill scans the git log and hot files and writes an architecture review page.
- R9. IF you use modular skills THEN keep them independent so you can run any one in any order. Reason: chained frameworks (G Stack, Superpowers, GSD) force you to rerun the whole pipeline if one step goes wrong.
- R10. IF you use a frontier model THEN use light, modular skills and let the model decide. Reason (speaker's view): Anthropic removed over 80% of its own system prompt for newer models. IF you use a weaker model THEN a heavy framework such as Superpowers may fit.
- R11. IF you install skills THEN stay selective; the speaker's own opinion is to avoid heavy guardrails that hold back the model.

## Features and facts mentioned (with version or date if given)
- The "grill-me" skill is the second most downloaded skill of all time on the skill leaderboard (per speaker, Aug 2026). The library has over 51 skills and over 13 million downloads.
- Skills named: grill-me, to-spec, to-tickets, implement (runs TDD), TDD, code review, writing-for-agents, improve-codebase-architecture.
- Compared frameworks: G Stack, Superpowers, GSD.
- Models named: Opus 5, Fable 5, GPT-5.6; "weak" models: Sonnet 5, DeepSeek (speaker's wording).

## Mistakes to avoid
- Letting the AI guess your context.
- Asking many questions at once.
- Embedding code in specs.
- Slicing work by layer.
- Writing tests after code.
- Long, wordy skills.

## Relevant for a non-developer business workflow (SEO/marketing agency, Cowork, scheduling, client deliverables)
- The grill-me interview (one question at a time, with a recommended answer) fits client onboarding and brief building.
- Write the agreed brief to a file so it survives the chat.
- Slice deliverables by outcome (one finished page) not by layer (all research, then all drafts).
- Keep skills short and put the check in a fresh session.
