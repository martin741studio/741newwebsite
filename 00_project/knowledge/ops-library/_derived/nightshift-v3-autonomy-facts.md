## Gap 1 — Self-healing beyond `Restart=on-failure`

1. IF a systemd unit on 741-agents-01 can hang (stuck, deadlocked) while still technically running, THEN `Restart=on-failure` will NOT catch it — add `WatchdogSec` + an `sd_notify(WATCHDOG=1)` heartbeat sent from inside the process's own work loop (after each real unit of work, not on a free-running timer), paired with `Restart=on-watchdog` or `on-failure`. [N05]
2. IF a unit has a slow or variable startup (the Chrome/Xvfb/noVNC browser stack), THEN use `Type=notify` with the process's own `READY=1` signal so the watchdog clock doesn't start — and doesn't kill it as "hung" — before startup has actually finished. [N05]
3. IF a 741-agents-01 process (batch runner or persistent `claude remote-control`) restart-loops on a permanent fault, THEN cap it with a rolling respawn budget (e.g. systemd `StartLimitBurst`/`StartLimitIntervalSec`) plus backoff (`RestartSec`), and once the budget is exhausted, park it in a clearly-flagged stopped state with the last error attached rather than looping forever or auto-resuming blind. [N08]
4. IF 741 wants this exact crash-loop-to-parked-state pattern pre-built rather than hand-rolled in systemd, THEN Bernstein (open-source, AI-agent-specific supervisor) is a concrete tool to evaluate — default respawn budget 3/60s rolling window, backoff `initial_backoff_ms × attempt` capped at `max_backoff_ms`, explicit `SessionParkedError` + manual `resume` on exhaustion. [N08, undated — re-verify numbers before copying]
5. IF 741-agents-01's systemd units report "active" after a reboot or crash, THEN that is orchestrator-level proof only — it does not prove the underlying work (a real agent task, a real browser session) actually completes; treat "active" and "the server is actually useful" as two different claims requiring two different checks (see Gap 4). [N11]

## Gap 2 — Update/patch cadence

6. IF 741-agents-01 auto-updates the Claude Code CLI (or the Desktop app it might later be paired with) without a check-after-update step, THEN that is a real, documented risk: a routine point release (v2.1.206, auto-updated 2026-07-14/15) silently flipped every existing scheduled task from bypass to manual permission mode with zero warning — unattended runs then stall on a prompt nobody answers. Run one scheduled/headless task by hand immediately after any version bump and confirm it does NOT stop on a permission prompt before trusting the queue to it. [N02]
7. IF 741 pins the Claude Code version to avoid this class of regression, THEN re-check it on a cadence anyway rather than freezing it forever — a single week in October 2026 (2.1.292–2.1.300) shipped multiple fixes for exactly the failure modes night-shift-v2 depends on: retry backoff limits, remote-control reconnect-after-sign-in-error, scheduled-wakeups silently not firing while a background task runs, and two separate multi-day memory leaks. Staying current is not optional once the server runs for days unattended. [N01]
8. IF 741-agents-01 is pinned to Node v22.23.3 (done 2026-10-14), THEN that line is Maintenance LTS (EOL 2027-04-30) — plan the move to Node 24.x (Active LTS from 2026-10-20, explicitly the "recommended target for most production apps") with lead time, not as an emergency migration; no patches ship at all for an end-of-life line regardless of severity. [N09, N10]
9. IF a Node security advisory lands for 741's line, THEN apply it within the same week (not same-day untested, not indefinitely deferred): inventory pinned versions → read the actual advisory → test in a branch (native-addon/Playwright-Chromium dependents are the likeliest breakage point) → roll out → gate future drift in CI. [N09]
10. IF the choice is "stay current" vs "don't break a working unattended setup," THEN the evidence from both the Claude Code changelog (gap-fix cadence) and the Node security-release pattern points the same way: small, frequent, tested updates beat large infrequent ones — the documented breakages above came from *not* checking after an update landed, not from updating too often. [N01, N02, N09]
11. No freshness-qualified source was found specifically for npm package or Playwright/Chromium browser-build update cadence (gap, noted below) — apply the Node pattern (same-week, test-then-roll, CI-gate) to those by analogy until a better source turns up.

## Gap 3 — Credential handling without a live human (OAuth/2FA at 3am)

12. IF a Claude Code process on 741-agents-01 hits "Please run /login" / a 401 at 3am with nobody there, THEN do NOT have the automated recovery path try an interactive `/login` loop — a documented case shows that path itself can get stuck (browser shows success, CLI never gets the callback, Enter just reopens the browser). The safer automated action is to back off and retry the original request once; the credential is often already valid again because another client (the batch token, Martin's phone, Martin's laptop) already refreshed the shared account-level login. [N03]
13. IF 741-agents-01 runs more than one Claude Code identity against the same account at once (batch `CLAUDE_CODE_OAUTH_TOKEN`, persistent `claude remote-control` full login, Martin's own devices), THEN a refresh race across those clients is a documented failure mode, not a hypothetical — 741's existing split (batch token kept deliberately separate from the Remote Control full login, decisions.md N43–N47) reduces but does not eliminate this, since Remote Control's own login is still one account-level credential Martin's devices may also touch.
14. IF 741 wants the night-shift's `--permission-prompts none` / `dontAsk` posture to fail safely rather than hang when something needs a human, THEN upgrade to `--permission-prompts none` (added v2.1.259, Sept 2026) — it denies-and-continues instead of leaving an unanswerable prompt, which matters specifically for 3am runs. [N04]
15. IF 741's current secret storage (`.secrets/` + `.env` as 600-mode plaintext files, copied 2026-10-14) needs to survive an unattended reboot with less plaintext-on-disk exposure, THEN `systemd-creds` (TPM-bound key if the CAX31 exposes a vTPM, else host-file key) is the direct next step that keeps the "no login needed" property already committed to — but don't build this pre-emptively; 741's current threat model (single operator, single trusted host, Tailscale-only remote access) doesn't yet require it, and systemd-creds itself has no audit trail or rotation. [N06]
16. IF 741-agents-01's deny rules (curl/ftp/scp/rsync/ssh outbound, `git push` to `main`, per night-shift-server-workflow.md §6) include any path with parentheses or any single malformed pattern, THEN re-verify they were actually enforced — a documented bug (fixed v2.1.260) let a path containing parentheses bypass the Bash sandbox entirely, and one bad pattern anywhere in the rule set silently disabled every other file-edit deny rule. [N04]

## Gap 4 — Recovery testing discipline

17. IF decisions.md's reboot test (N43–N47: rebooted the server, confirmed 6 systemd units + CDP port + noVNC back up within ~25s) is treated as proof the stack is reboot-proof, THEN that is orchestrator-level verification only — the equivalent, stronger test is whether the browser/Remote-Control/batch-runner stack can complete one real task end-to-end right after the reboot, not just whether the ports are listening. "A deployment rollback completing successfully does not prove checkout recovered" is the general form of this gap. [N11]
18. IF 741 schedules a recurring drill rather than treating the one-off reboot test as sufficient forever, THEN define the failure mode, blast radius, and abort condition in writing before each drill (e.g. "kill -9 the claude-remote-control process, confirm it is back and able to answer a real prompt within N seconds" — not "see what happens"), and re-run after any change to systemd units, permissions, or the Tailscale/firewall setup, not on a fixed calendar alone. [N11]
19. IF Martin or an agent judges "was the night/the reboot/the drill OK," THEN use a three-way rating — pass / pass-with-finding / fail — instead of binary; a run that technically completed but needed an undocumented manual fix or an access path nobody wrote down is a "pass with finding" that should generate a tracked follow-up (owner + due date), not a silent pass. [N11]

## Gap 5 — Logging and alerting on failure

20. IF 741-agents-01 needs proof its agent processes are alive and making progress (not just that systemd says "active"), THEN add heartbeat/dead-man's-switch pings sent after each real unit of work, with period/grace tuned per job — this is the standard, lightweight fix for exactly the "systemd says active but nothing is actually happening" gap. [N07]
21. IF Martin is deciding whether to build a second monitoring stack for server health, THEN don't — `canary/SKILL.md` already owns outage-watch and alerting (Telegram escalation, SEV1 paging, allowlist-gated self-heal, "no outside watcher for the runner itself" already flagged as open in its own decisions.md C6) — wire the server heartbeat into that same alerting path as one more check row, not a parallel system with its own thresholds and its own fatigue risk. [N07, and 741's own canary/SKILL.md]
22. IF 741 picks a dead-man's-switch tool, THEN plan for the monitor itself to fail occasionally — even the reference implementation for this pattern is explicit that a one-person operation can have a multi-hour or multi-day outage of the monitor, which is the same risk 741's own canary decisions.md already flagged and deferred ("revisit after first real outage"). A second, independent, low-effort check (an external ping on the dead-man's-switch service's own status, or noticing a daily digest stopped arriving) is the cheap mitigation. [N07]

## Gap 6 — Anthropic/Claude-Code-specific resilience

23. IF 741's night-shift runner treats `--max-turns`/`--max-budget-usd` as a hard, provable stop, THEN downgrade that assumption — as late as v2.1.299 (Oct 14, 2026) there was a documented bug where a self-resubmitting mod could blow past both caps. Keep both flags, but also keep an external wall-clock timeout (`timeout`/`gtimeout`, or systemd `RuntimeMaxSec`) as the real backstop, and check the run's own exit code/JSON output rather than trusting the flags alone. [N01]
24. IF 741-agents-01 runs `claude agents` background sessions or `/loop` across a process restart, THEN scheduled wakeups have, in documented released versions, silently failed to fire while a background task was already running — this is exactly the kind of silent miss a heartbeat check (Gap 5) is meant to catch, don't rely on "it should have fired." [N01]
25. IF 741 upgrades the night-shift runner's permission posture, THEN `--permission-prompts none` (v2.1.259+) is the currently-documented, purpose-built flag for "CI or scheduled tasks where waiting for input is not an option" — it denies rather than hangs, a meaningfully different failure mode than today's `dontAsk`. Re-run 741's existing permission test (decisions.md N28: curl denied, writes outside the scoped folder denied) after adopting it, since it changes default behaviour for anything outside the allowlist. [N04]
26. IF 741 relies on `claude logs/stop/kill/rm` or daemon subcommands inside a health-check script to infer token health, THEN don't — a documented bug (fixed v2.1.293) had those commands sometimes sign the user out merely because a token was *about to* expire, not because it was actually dead; that's a false signal for an automated recovery path to act on. [N01]
